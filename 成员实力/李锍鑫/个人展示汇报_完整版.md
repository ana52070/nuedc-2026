#### 背景

TI杯电子设计竞赛要求参赛队伍在4天3夜内完成一个完整的电子系统。2025年的E题为"简易自行瞄准装置"：用摄像头识别目标，用激光笔进行瞄准跟踪。这本质上就是一个小型化的"视觉伺服跟踪系统"——和我在公司实习期间做的 AI 自动跟踪摄像系统在原理上高度同构。

#### 我的角色

我独立负责 STM32F103C8T6 端的全部固件开发，包括传感器数据融合、电机控制算法、通信协议解析三大核心模块。K230 视觉模块的深度学习目标检测由另一位队友负责。

#### 技术方案

系统架构：K230 视觉模块负责目标检测，通过 UART1 将目标的 X/Y 坐标发送给 STM32；STM32 运行 PID 控制算法，通过 RS485/ModBus 协议驱动两台步进电机，带动激光笔瞄准目标。



![system_architecture](assets/system_architecture.svg)





#### 核心亮点

**亮点一：5中断协同架构——裸机环境下的"多任务调度"**

在没有 RTOS 的裸机环境下，我设计了 5 个中断的协同工作架构：

| 中断 | 功能 | 频率 |
|---|---|---|
| TIM4 定时器中断 | PID 计算（每 40ms 触发一次）+ 按键扫描（1ms tick） | 1ms / 40ms |
| TIM1 定时器中断 | ModBus 响应帧解析（从电机的7字节应答中提取位置） | 事件驱动 |
| UART1 接收中断 | K230 视觉坐标数据接收 | 115200bps 异步 |
| UART2 接收中断 | 电机1（Y轴）ModBus 应答接收 | RS485 异步 |
| UART3 接收中断 | 电机2（X轴）ModBus 应答接收 | RS485 异步 |

这不是简单的"把中断使能打开"——难点在于：5个中断的优先级安排、临界区保护、以及中断与主循环之间的数据同步。我采用"生产者-消费者"模式：中断负责"生产"数据（存入全局缓冲区），主循环负责"消费"数据（执行控制逻辑）。

**亮点二：串口状态机解包——用3个静态变量替代库函数**

K230 发送的每一帧数据是 7 字节的自定义格式。我设计了一个基于3个静态变量的确定性状态机来解析，而不是依赖任何第三方库：

- `rx_state`：记录当前解析状态（IDLE → RECEIVING → COMPLETE）
- `rx_index`：记录已接收的字节数
- `rx_buffer[7]`：帧缓冲区

状态机有3个状态，每个状态只有一种出口——确定性远高于传统队列式的帧解析。这段代码在比赛现场从未出现解析错误。

**亮点三：坐标滤波——动态阈值 + EMA 滑动平均**

K230 的视觉检测会有噪声：光照变化、目标抖动、偶尔的误检测都会产生异常坐标。我设计了一个两级滤波策略：

1. **异常检测**：如果新坐标与上一帧坐标的欧氏距离超过动态阈值（基于连续帧的历史方差计算），则判定为"跳变"，丢弃该帧
2. **EMA 滑动平均**：正常坐标通过指数移动平均（α = 0.5）平滑，减少高频抖动

效果：在目标静止时，电机几乎无微颤。

#### 背景

传统的校园无人车方案（如无人配送、无人巡逻）大多依赖预先建立的高精度地图（SLAM）。但建图成本高、维护困难——一旦校园道路翻修或新增减速带，地图就得重做。我的目标是：**让机器人不需要地图，直接输入一个RTK坐标就能自主导航过去**。

这个想法源于一个朴素的观察：人开车去一个陌生的地方，不需要先扫描一遍整条路——看一眼目标位置，结合实时感知，就能开过去。为什么机器人不行？

#### 我的角色

这是我**独立开发**的项目——从仿真到实物、从驱动到导航栈、从第一行代码到全部技术文档，全程一人完成。项目历时约 5 个月，产出 20+ 篇技术文档。

#### 技术方案

核心思路：**双层定位融合 + 无地图导航**。

![robot-architecture](assets/robot-architecture.svg)



**双层定位融合（最关键的设计）**：

- **第一层（局部）**：FAST-LIO2 利用 Livox Mid-360 点云进行帧间匹配，提供 10Hz 高频里程计（位置精度约 1cm，角度精度约 0.1°）。它告诉机器人"我往前走了 0.5 米、往右转了 3 度"
- **第二层（全局）**：RTK-GPS 提供厘米级绝对位置修正。它告诉机器人"你现在的绝对坐标在哪里"
- **EKF 融合**：robot_localization 的扩展卡尔曼滤波器融合两者——FAST-LIO2 提供连续、高频的位置增量；GPS 提供离散的、低频的绝对锚定

可以这样理解：FAST-LIO2 是一个"本地惯性导航"，非常精确但会慢慢漂移；GPS 是一个"卫星锚点"，绝对准确但偶尔信号不好。EKF 就是那个聪明的"和事佬"——信任 FAST-LIO2 的短时精度，但用 GPS 来防止漂移积累。

#### 核心亮点

**亮点一：v1 → v2 架构演进——敢于推翻自己**

v1 方案使用的是"轮式里程计 + GPS + EKF"的传统架构。但在实际测试中，我发现轮式里程计存在根本性的精度问题：Yahboomcar 底盘的轮式里程计速度不确定度约 ±5cm/s，对于最大速度仅 26cm/s 的车来说误差率高达 20%。在 GPS 两次更新之间（50-200ms），EKF 只能依赖这个"不太靠谱"的里程计——导致轨迹出现周期性的"振荡式歪斜"。

v2 的核心改进是引入 FAST-LIO2（LiDAR 惯性里程计）替代轮式里程计，同时将计算平台从 NVIDIA Jetson Xavier NX 迁移到 Intel N100 Mini PC。这个改动带来三重收益：

| 维度 | v1（旧方案） | v2（新方案） | 改进 |
|---|---|---|---|
| 位置增量精度 | ±5cm/s（轮式） | ±0.5cm/s（LiDAR） | **10倍提升** |
| GPS丢失鲁棒性 | 秒级漂移，< 5 秒不可用 | FAST-LIO2 独立维持数分钟 | "质的飞跃" |
| 平台部署难度 | Docker + ARM 交叉编译 | x86 原生 apt install | 从2天缩短到2小时 |



**亮点二：GPS 降级鲁棒性——不让机器人"失明"**

我基于 UM982 RTK 驱动输出的协方差矩阵，设计了一个 GPS 质量自适应策略：

| GPS 状态 | 协方差范围 | 系统行为 | 导航效果 |
|---|---|---|---|
| RTK Fixed | < 0.001 m² | GPS 高权重修正 | 最优 |
| RTK Float | 0.001 - 0.25 m² | GPS 中等权重，LIO 为主 | 良好 |
| DGPS / SPP | 0.25 - 10 m² | GPS 低权重，LIO 主导 | 可接受（短期） |
| 无 GPS | 无数据 | 纯 FAST-LIO2 | 可接受（数分钟） |

这个设计让机器人在 GPS 信号降级时不会突然"发疯"——它平滑地从"GPS 主导"切换到"LiDAR 主导"，像一个经验丰富的司机在大雾中降低速度但仍然安全驾驶。





**亮点三：完整的开发文档体系**

作为独立开发者，我建立了从项目介绍、TODO清单、仿真环境搭建、硬件迁移到进度汇报的全套文档（20+ 篇），覆盖主线开发 + 6 条支线（Jetson 刷机、Docker 部署、Mid-360 环境、RTK 驱动、USB 串口绑定、电源规划）。这不是"做了才写"——而是"写的过程就是思考的过程"。

### 2.1 AI 自动跟踪系统优化 ⭐ 最核心亮点

#### 2.1.1 解决了什么问题？

公司原有 AI 自动跟踪方案存在**两个致命痛点**，直接限制了产品的市场竞争力：

| 痛点 | 原方案 | 业务影响 | 我的新方案 |
|------|--------|---------|-----------|
| 机芯绑定 | **只能用海康机芯** | 供应链单一、议价能力弱、无法响应客户定制需求 | 适配**任意品牌机芯** |
| 变倍方式 | **只能数字变倍**（放大像素，画质劣化） | 远距离目标放大后模糊，实际可用场景受限 | 数字变倍 + **光学变倍**（物理变焦，画质无损） |

> **一句话：** 原方案是"绑死海康、画质打折"，新方案是"想用谁用谁、远近都清晰"。



##### 方案：光学变倍 PID 自动跟踪 — 整套系统的"奇思妙想"

这是整个项目中最具创新性的技术突破。

**为什么光学变倍 + AI 跟踪不好做？** 因为 AI 识别给出的是 XY 坐标 + 框大小，云台控制处理 XY，而变倍控制处理框大小——这两个回路如果耦合在一起就会互相干扰：云台在动，框在变，变倍也在动，三者互相"打架"。

**我的设计思路：完全解耦。** 将变倍控制和云台控制拆成两个独立的闭环：

```
AI 识别框高度（目标变量）
        │
        ▼
  ┌─────────────┐
  │  PID 控制器  │ ← 实时计算变焦指令（放大/缩小）
  └──────┬──────┘
         │
    ┌────▼────┐      ┌──────────┐
    │ 光学变倍 │      │ 云台 PID  │ ← 独立闭环，控制 XY 跟踪
    │  机芯   │      │  控制器   │
    └─────────┘      └──────────┘
         │                 │
    互不干扰，各自独立闭环
```

> **比喻：PID 就像一位驾驶员保持车距——**
> 前方车辆（吊具）离远了，识别框变小 → PID 输出**放大**指令，追上目标；
> 前方车辆太近了，识别框变大 → PID 输出**缩小**指令，拉开视野。
> 整个过程全自动、实时调节，不需要人工干预。

**以识别框高度为目标变量**，PID 实时计算变焦指令，保证目标始终处于最佳视野范围。这听起来简单，但背后的"奇思妙想"在于：**把图像空间的 AI 输出量（像素级别的框高度）直接映射到物理空间的机械控制量（变倍电机的速度和方向），跨域做了闭环控制。**

#### 2.1.3 RK3588s 端侧 AI 部署 — 从服务器到芯片的完整落地

产品最终不能绑在 PC 上，必须部署到嵌入式端侧。我完成了完整的端侧 AI 部署闭环：

| 环节 | 方案 | 关键数据 |
|------|------|---------|
| **模型选型** | YoloV8 → YoloV11-obb → yolov11s_size640_hbb_fp16.rknn | 从检测到旋转框，再精简到水平框满足业务需求 |
| **NPU 推理** | RK3588s 三核 NPU 并行 | 单帧推理 **72ms**，3 核并行约 **15 FPS**，NPU 占用率 **90%** |
| **视频解码** | RGA 硬件加速 | 2K 视频解码仅 **15ms**，不占用 CPU |
| **帧调度器（奇思妙想）** | "追赶最新帧 + 填补缺失帧" | NPU 推理与视频流异步，帧到达顺序可能乱序，调度器自动跳过过期帧、补齐缺失帧 |
| **配置热重载** | 参数文件监控 | 修改配置文件后程序自动重载，无需重启 |

> **调度器的"奇思妙想"：** NPU 推理是异步的，视频帧可能乱序到达。普通的做法是队列+等待，但这会引入延迟。我设计了一个轻量级调度器：每帧带时间戳，调度器检查"如果当前已处理到更新的帧，就跳过旧帧；如果发现中间缺了一帧，就用最近的有效结果填补"。这个设计让端侧推理在 15 FPS 下仍然保持流畅的跟踪体验。

**数据集构建：** 在曹妃甸现场采集并标注了 **2261 张**图像（白天/黑夜约 1:1），确保模型在昼夜切换场景下的鲁棒性。

**软件架构：** 采用 **8 线程并行架构**，将视频取流、AI 推理、PTZ 控制、通信、日志等模块分离，各司其职，互不阻塞。





通过引入ByteTrack模块，为PID的输入控制数据增加了滤波+预测两大功能，滤波：把 YOLO 的抖动抹平，计算出稳定的中心点。预测：从位置的变化中，计算出稳定的**速度矢量，并根据速度计算出延迟帧之后的预测值，**将预测值作为PID算法的输入，从而实现跟随响应更快的效果。

| 变倍完毕后虚焦 | 光学变倍后画面短暂模糊 | 正在探索**区域聚焦 + 自动聚焦 + 虚焦检测**的组合方案 |

### 2.2 网络相机控制系统（STM32 / Linux）

#### 2.2.1 为什么做这个？

传统方案中，控制相机云台需要通过这条链路：

```
RS485 → 录像机（几千元）→ 云台
```

录像机价格高昂，但在这个场景下**只用到了它的云台控制功能**——相当于买一辆卡车只为了用它点烟器。

**我的目标：用不到 100 元的芯片，替代几千元的录像机，通过网络直接控制相机云台。**

#### 2.2.2 阶段一：STM32 裸写 ONVIF 协议栈

> *"网上的资料都是 Python/C++ 调用封装好的库，但在单片机上，所有轮子都得自己造。"*

在资源极度受限的 **STM32F407**（192KB RAM，1MB Flash）上，从零构建 ONVIF 协议栈：

| 从零实现 | 技术细节 | 难度 |
|---------|---------|------|
| HTTP Digest 认证 | MD5 哈希、nonce/cnonce/response 等加密字段的**手动计算与拼接** | 需要透彻理解 RFC 2617 |
| SOAP 报文处理 | XML 报文的手动构造与解析，没有现成库可用 | 内存受限下操作 XML 需要极细致的空间管理 |
| LWIP 协议栈对接 | 底层 socket 编程，与 LWIP 协议栈逐层对接 | 需要理解 TCP/IP 栈的每一层 |

**"一控五"方案突破 —— 又是一个"奇思妙想"：**

在 STM32 上，每创建一个相机控制对象约消耗 2% 内存，而基础功能（系统+通信+UI）已经占用 **96%**。按常规思路，控制 5 个相机需要 5 个对象 = 10% 额外内存 → 直接 OOM 崩溃。

**我的方案：单对象 + 动态切换属性。** 不创建多个对象，而是用一个对象，在每次控制前动态切换它的目标 IP、认证凭据、通道号等属性。这样内存增长几乎为零，但实现了同时控制 5 个海康摄像头。

![image-20260707222819855](assets/image-20260707222819855.png)





> 这个"奇思妙想"的本质是：**用时间换空间**——牺牲纳秒级的属性切换时间，换取 10% 的宝贵内存。

### 2.3 系统镜像深度裁剪

#### 2.3.1 为什么做这个？

通用 Linux 发行版（如 Ubuntu Server）是"瑞士军刀"——什么都能干，但什么都带着冗余。产品上需要的是"手术刀"——精确、轻量、快速。

AI 跟踪程序最终要部署到 RK3588s 端侧，通用镜像启动慢、占用大、后台进程多，**直接影响产品的开机体验和稳定性**。

#### 2.3.2 裁剪成果

| 指标 | Ubuntu 官方镜像 | Debian Lite | 裁剪 Kernel 版 | 裁剪 Kernel+Rootfs 最终版 | **总优化幅度** |
|------|:---:|:---:|:---:|:---:|:---:|
| 根文件系统 | 5.7GB | 1.7GB | 1.7GB | **1.4GB** | ↓**75%** |
| 内核大小 | 65MB | 55MB | **42MB** | **42MB** | ↓**35%** |
| 冷启动时间 | 39.98s | 13.01s | 5.49s | **5.43s** | **7.3 倍加速** |
| 内存占用 | 195MB | 236MB | 201MB | **183MB** | ↓**6%** |
| 后台进程数 | 224 | 188 | 169 | **153** | ↓**32%** |
| 内核动态模块 | 36 个 | 10 个 | **0 个** | **0 个** | **完全静态化** |

> **关键洞察：** 最大的收益不是空间（虽说省了 4.3GB），而是**时间**。从按下电源到程序就绪，从近 40 秒缩短到不到 6 秒——这个差异在客户现场就是"能用"和"难用"的区别。

#### 2.3.3 裁剪方法论

我将整个裁剪过程系统化为一套可复用的方法论，并沉淀为 **52 页实战文档**：

| 裁剪层次 | 方法 | 关键技术决策 |
|---------|------|------------|
| **Kernel 裁剪** | AI 辅助 menuconfig 配置决策 | 一键关闭所有无用驱动和子系统，精确保留项目需要的模块 |
| **Rootfs 裁剪** | 四步清洗法 | 软件包精简 + 文档清理（50-100MB）+ 语言包清洗（30-50MB）+ Apt 缓存清理（20-100MB） |
| **Boot 优化** | 延迟启动 + 并行化 | 非必要服务延迟加载，关键服务并行启动 |

**创新点：extboot 分区设计**

将所有系列板卡的设备树（Device Tree）全部打包到 extboot 分区，通过**硬件 ID 自动识别并切换**对应的设备树。这样**刷一次镜像就能兼容全系列板卡**，不用为每款板子单独维护镜像文件——这又是一个"奇思妙想"，把多条维护线合并成一条。

### 五、协会管理经验与职场能力的关联

回头看，协会的管理工作给了我三个宝贵的职场预演：

**1. 统筹规划能力 = 项目管理能力的雏形**

**2. 从管事到管人 = 领导力的起点**

作为副会长，最难的从来不是技术问题，而是"如何让团队里的每个人都愿意动起来"。我学会的方法不是"命令"，而是**用数据和可见的成长去激励**——当成员看到自己在飞书看板上的任务一个个变成绿色，看到自己的项目从"待启动"走到"已交付"，这种成就感比任何口头催促都管用。在公司环境中，"推项目"而不"催人"的能力，同样关键。

在协会中我反复强调传承的价值，这不仅是一句口号。我体会到一个朴素的道理：**你教会别人，项目才能持续运转；你藏着一手，最后累死的是你自己。** 在公司实习中，我延续了这种思维——主动分享技术方案、为新同事整理入门文档、在项目中积极配合同事。这不是"多做事吃亏"，而是让团队效能最大化的理性选择。

#### 技术亮点

写博客谁都会，但我的玩法有点不一样：

**自动化发布流程。** 我写了一个 `upload_with_llm.py` 脚本，它会自动检测文件变更、调用 LLM 生成规范的 commit message、然后 `git add .` + `git commit` + `git push` 一条龙。我写完文章只需要在终端敲一个命令，剩下的全部自动化。同时还有一个 `update_index_with_llm.py`，自动识别我更新了哪个板块（blog / projects / guide），只更新对应板块的目录索引。

**这意味着什么？** 我把"写博客"这件事本身也工程化了。不是每次手写 commit message，而是让 AI 帮我理解我写了什么、自动生成合适的提交信息。这就是我说的——**让AI为我工作**。

> 技术架构：VitePress 静态站点 + Teek 主题插件（自动 frontmatter + 自动侧边栏）+ GitHub 托管 + Vercel 部署 + 自建 LLM 脚本自动 commit & push。

#### 它和公司工作有什么关系？

在公司我写了大量技术文档——从《ONVIF开发手册》到《通信格式规范 V1.3》到《裁剪实战文档52页》。我在公司推动"隐性知识文档化"，而 chuiyu.wiki 就是我把这个理念从公司延伸到了**我自己的终身学习中**。

> 知识不只是写给同事看的交接文档，还可以是写给全球开发者的技术博客。前者解决的是"团队协作成本"，后者解决的是"知识复利效应"——每一篇文章都是一笔能持续产生价值的资产。

### 4.3 my_model_api —— 让多个AI模型"为我所用"

#### 这是什么？

一个基于 **Next.js 16 + React 19 + Tailwind CSS 4** 的 LLM API 管理仪表盘。简单说就是一个"大模型API管理台"——把多个 AI 服务商的 API Key 统一管理、连通性测试、模型列表查看、额度余量监控，全部在一个网页里搞定。

目前我已经配置了 **5个提供商**：Opencode Go、Agens Free、ModelScope Free、DeepSeek、中转站。

#### 为什么做这个？

现在市面上的大模型太多了，每家都有自己的 API、自己的 Key 格式、自己的认证方式。OpenAI 用 `Bearer`，Anthropic 用 `x-api-key`，DeepSeek 又是另一个格式……每次切换模型都要去翻文档、查 Key、测试连通性，烦得不行。

我想：**为什么不做个"仪表盘"，像管理设备一样管理这些模型 API？**

#### 架构设计（我很骄傲的几个点）

**前端直连 localStorage —— 密钥只存在浏览器里。** 我不在服务端存任何 API Key。你输入 Key 之后它直接写进浏览器的 localStorage，服务端完全看不到。这样即使服务器被黑了，攻击者也拿不到任何 Key。

**服务端代理 `/api/proxy` —— 跨域处理。** 通过 Next.js 的 API Route 做代理，统一处理 OpenAI（Bearer）和 Anthropic（x-api-key）两种认证头，浏览器端完全不用管跨域问题。

**密码保护。** 查看/复制密钥前，需要先输入密码验证。不是谁打开网页就能看到 Key。

**环境变量注入。** 支持通过 `.env` 预配 API Key、Opencode Cookie/ServerId、控制台密码——部署时直接注入，不需要手动填写。

#### 核心组件

| 组件 | 功能 |
|:--|:--|
| `ProviderCard` | 左侧 3px 信号条自动变色（绿色=打通 / 红色=断连 / 黄色=测试中 / 灰色=未配置），支持 API Key 输入、连通测试、模型列表、额度余量 |
| `ApiKeyInput` | 密码验证后才能显示/隐藏/复制 |
| `ModelList` | 默认展示前 10 个模型，点击展开全部 |
| `QuotaSection` | 根据不同 provider 的 parser 解析不同格式的额度响应 |
| `ConnectivityBadge` | 四种状态 + 脉冲动画 |

视觉风格上，我故意没走常见的"蓝白科技风"——而是用了暖色调：奶油色底 `#faf8f4`、深棕色文字 `#2d2a26`、陶土色强调 `#d97757`。我想让这个工具看起来**不像冷冰冰的后台管理系统，而像一个有温度的"工作室"**。

#### 它和公司工作有什么关系？

在公司我裸写了 ONVIF 协议栈——HTTP Digest 认证、SOAP 报文的 XML 构造/解析、nonce/cnonce/response 加密字段的手动计算。做这些事让我明白了一个道理：**理解协议才能管理协议。**

my_model_api 看起来是个"前端项目"，但它的核心价值不在前端，而在于——我对不同 LLM 的 API 协议做了深入理解：OpenAI 和 Anthropic 的认证方式为什么不同？RESTful 的 `/v1/chat/completions` 和 `/v1/messages` 在请求体和响应体的格式差异是什么？我帮每个 provider 写了专属的 parser，才能在前端统一展示成"信号条 + 模型列表 + 额度余量"。

> 就像 ONVIF 协议栈一样——理解底层，才能优雅地管理上层。

### 4.4 这三个产物，共同说明了一件事

回到这一章开头的那句话：**"在AI时代，我不只是'使用AI'，我是'让AI为我工作'的人。"**

- chuiyu.wiki 让我把 AI 变成了我的**写作搭档和编辑器**——自动生成 commit message、自动更新目录索引。
- N100 小龙虾让我把 AI 变成了我的**运维助手和技术参谋**——透过 WhatsApp，它在任何时候等我，帮我搜资料、看日志、管服务器。
- my_model_api 让我把 AI 变成了**可管理的资源**——不是被动地用一个模型，而是主动地把多家模型的 API 集中管理、测试、调度。

这三个产物，从文档写作（内容层）到服务器运维（基础设施层）到 API 管理（协议层），构成了一个完整的闭环。它们是我在 AI 时代做的第一次"系统性探索"。

> **关键是：我不是等着 AI 来改变我，而是我主动去改造 AI 让它为我所用。**
